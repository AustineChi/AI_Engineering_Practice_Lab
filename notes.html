    Start here: the big picture

    Read this first. It is the map that every other topic hangs on.

    The one-line ideaAI engineering is building a system around a model: get good data, train or choose a model, measure it honestly, ship it safely, and keep watching it. Most problems are found by asking "which stage is failing?" and fixing the earliest broken one.

    Two running examples used in all notes

    A. The fraud model (classic ML)

    • Input: rows of transactions (amount, time, merchant…)
    • Output: fraud / not fraud
    • Only ~1% of rows are fraud (imbalanced)
    • Used to explain: data splits, leakage, metrics, training problems, drift

    B. The policy assistant (LLM app)

    • Staff ask questions about company policy PDFs
    • Answer must be correct, cited, and respect who may see what
    • Used to explain: RAG, prompts, agents, security, evals, serving, cost

    The classic 7-step ML lifecycle

    1 Collect data → 2 Prepare data → 3 Choose model → 4 Train → 5 Evaluate → 6 Tune → 7 Deploy & monitor ▲___________________________ loops back all the time ___________________________|
    • Real projects are loops, not a straight line. A production problem sends you back to data.
    • Data work (collecting, cleaning, labelling) takes most of the time. "70–80%" is a rule of thumb, not a measured fact.

    The picture of an LLM application (example B)

    Three habits that answer most questions

    1. Measure before you change. Profile before optimising; read traces before guessing; get a baseline before tuning.
    2. Find the earliest failing stage. Data → retrieval → generation → validation. Fixing a later stage cannot repair an earlier one.
    3. Change one thing at a time. Otherwise you cannot tell what helped.

    The decision order for LLM problems

    1. Prompt / context engineering (cheapest, fastest) 2. RAG (missing or changing knowledge) 3. Fine-tuning (style, format, stable behaviour) and: API first → self-host later (when volume, data residency or customisation justify it)
    Remember
    • Pipelines loop; production issues send you back to data.
    • Diagnose the earliest failing stage first.
    • Prompt → RAG → fine-tune; API → self-host.

    1. Data, splits and leakage

    Example A: the fraud model. Most "too good to be true" results start here.

    The one-line ideaYour evaluation is only honest if the model has never seen, or been influenced by, the data it is tested on. Leakage is any way information sneaks across that wall.

    The three splits

    SplitUsed forRule
    TrainingFitting the model (and fitting scalers/imputers)The only place you "learn" from
    ValidationChoosing models, tuning hyperparameters, early stoppingUsed many times
    TestFinal, unbiased scoreTouch once, at the very end. If you tweak based on test results, it becomes a second validation set and the score is optimistic ("indirect overfitting")

    Types of leakage (and the fix for each)

    LeakWhat happensFix
    Preprocessing leakYou scale or impute using statistics from all data, so test info enters trainingSplit first. Fit scaler/imputer on training only, then apply to val/test. Use a scikit-learn Pipeline
    Target / feature leakA feature encodes the label, or isn't available at prediction time (e.g. "chargeback filed")Only use information that exists at the moment of prediction ("point-in-time")
    Duplicate leakSame or near-same rows land in both train and test; model memorises themDeduplicate before splitting; group related rows
    Time leakRandom K-fold on time-ordered data lets the future train the pastChronological split: train on past, validate on later periods
    Red flag A model gets 99.8% on its first try. Suspect leakage (duplicates, a label-encoding feature, bad split) before celebrating.

    Class imbalance

    • With 99% legitimate transactions, a dummy model that always says "legit" scores 99% accuracy and catches 0% of fraud. Accuracy misleads.
    • Use precision, recall, F1, PR curves (see Topic 2) instead.
    • stratify=y in train_test_split keeps class proportions approximately the same in each split (not guaranteed identical).
    • Model predicts only the majority class? Check class imbalance, loss weighting (class weights), the learning rate, and the threshold.

    Is the training data representative?

    • Coverage gap: great on daytime photos, fails at night, because night images were missing from training. Fix the data, not the architecture.
    • Shortcut learning (spurious correlation): 98% accuracy but the model looks at a corner watermark. Inspect with Grad-CAM heatmaps.
    • Always check performance on slices (night vs day, region, customer segment). Averages hide failures.
    Remember
    • Split first, then fit preprocessing on train only.
    • Test set: once.
    • Time data → time-based split.
    • Great score on attempt one = look for leakage.
    • Imbalanced data → never trust accuracy alone.

    2. Metrics and choosing models

    Example A again: how do we know the fraud model is good enough, and which one to ship?

    The one-line ideaA single number never tells the whole story. Pick metrics that match the cost of each kind of mistake, and compare models under identical conditions.

    The confusion matrix in words (fraud = "positive")

    TermMeaningFormula
    TP / FPFraud caught / legit wrongly flagged
    FN / TNFraud missed / legit correctly passed
    PrecisionOf the ones I flagged, how many were truly fraud?TP / (TP+FP)
    Recall (TPR)Of all real fraud, how much did I catch?TP / (TP+FN)
    TNROf all legit cases, how many did I correctly pass?TN / (TN+FP)
    F1Balance of precision and recallharmonic mean

    You will meet TPR and TNR again when we validate LLM judges (Topic 10). Same idea, different system.

    Thresholds and curves

    • A classifier outputs a probability. The threshold turns it into yes/no. 0.5 is only a default.
    • Choose the threshold on validation data using the cost of false positives vs false negatives (missing fraud vs blocking a real customer).
    • ROC-AUC measures ranking ability across all thresholds. A model can have high ROC-AUC and still poor precision at your chosen threshold, especially when positives are rare. Look at the precision-recall behaviour, class prevalence and the threshold.
    • Calibration: do "90% confident" predictions come true 90% of the time? Big neural nets are often overconfident even with low training loss. Fix with post-hoc calibration such as temperature scaling.

    Comparing models fairly

    • Keep identical: data splits, preprocessing, metrics, test conditions.
    • Variance: scores vary between runs. Repeat with several seeds/splits and report the spread, not one number.
    • Seeds help but don't guarantee identical results: some GPU kernels and distributed operations are nondeterministic, and environments differ.
    • Similar quality? Then pick on latency, cost, reliability, maintainability, not a tiny accuracy edge.

    Before "improve accuracy by 5 points"

    1. Clarify the real metric and business goal.
    2. Get a baseline.
    3. Analyse errors by slice (where does it fail?).
    • Pretrained vs from scratch: decide using task fit, data available, compute budget, licence, latency and quality needs. Pretrained usually saves a lot.
    • Slices: new model worse for one customer segment → evaluate by segment and check data coverage; aggregate metrics hide this.

    Explaining models

    • SHAP values show how much each feature pushed one prediction up or down. Useful for regulated stakeholders; document their limits.
    • Importance ≠ causation. A feature the model uses a lot is not proven to cause the outcome.
    Remember
    • Pick the threshold from costs, not habit.
    • High AUC ≠ good precision at your threshold.
    • Report variance, compare under identical conditions.
    • Always diagnose (baseline + error slices) before tuning.

    3. Training and debugging neural networks

    Reading loss curves and PyTorch gotchas. Most debugging questions are "symptom → likely cause".

    The one-line ideaTraining repeats: forward pass → compute loss → backward pass (gradients) → optimiser step → clear gradients. Every bug shows up as a strange loss curve or a strange resource graph.

    One training step

    loss = loss_fn(model(x), y) # forward + loss loss.backward() # compute gradients optimizer.step() # update weights optimizer.zero_grad() # clear gradients (PyTorch ACCUMULATES by default)

    Loss-curve symptom table

    You seeLikely meaningFirst things to try
    Train loss ↓ , validation loss ↑Overfitting (memorising)Early stopping near validation minimum, dropout/weight decay, more data/augmentation, fewer epochs
    Both high and flat from epoch 1Underfitting, bad learning rate, or broken labels/feature alignmentCheck labels and features, tune learning rate, bigger model
    Loss → NaNExploding gradients (LR too high), extreme inputs, log(0), divide by zeroLower LR, clip gradients, normalise inputs, fix the loss
    Gradient norm grows every step, then crashExploding gradientsGradient clipping, lower LR, check normalisation layers
    Early layers don't updateVanishing gradients (sigmoid/tanh in deep nets)ReLU-type activations, residual connections, normalisation
    Validation loss lower than training loss early onUsually normal: dropout is on in training but off in eval; training loss is averaged over an epoch of improving weightsNothing; it's not a bug
    Loss won't drop even on a tiny batchA bug in the loop/loss/labelsRun the "overfit a single batch" test

    Sanity checks

    • Overfit a single batch: train on ~8 samples. Loss should go near zero. If not, the model, loss, labels or optimiser are wired wrong.
    • Unit-test the architecture (shapes, one forward/backward) before an expensive multi-hour run.
    • Shape error mat1 and mat2 shapes cannot be multiplied (64x128 and 256x10) → inner dimensions differ: the layer expects 256 inputs but got 128.
    • Device error ("expected all tensors on same device") → move model and data to the same device.

    PyTorch gotchas

    MistakeResult
    Forgot optimizer.zero_grad()Gradients pile up → erratic, oversized updates
    Forgot model.eval()Dropout stays active, BatchNorm keeps updating → inconsistent predictions
    Forgot torch.no_grad() in validation/inferencePyTorch builds a graph you don't need → memory spike when validation starts
    torch.log(probs) with zeros-inf/NaN → clamp with a tiny epsilon, or use stable combined losses (F.cross_entropy, BCEWithLogitsLoss)

    eval() and no_grad() solve different problems; inference normally uses both.

    Stabilisers you should recognise

    • Learning-rate warmup: start tiny, ramp up. Early on weights are random and Adam's statistics are noisy, so big steps destabilise training. Standard for transformers.
    • Gradient clipping: cap the gradient norm so one outlier batch can't blow up training.
    • Very large batch without adjusting LR: fewer updates, can converge to sharper minima that generalise worse. The relationship is nuanced.
    • Early stopping: stop when validation stops improving.
    • bf16 vs fp16: see Topic 4.

    Speed and data loading

    • GPU at 15%, CPU at 100% → the data pipeline is the bottleneck. Profile first, then raise num_workers, use pin_memory=True, precompute transforms.
    • 500 GB dataset that doesn't fit in RAM → IterableDataset streaming shards (WebDataset / Parquet).
    • Save with model.state_dict() (weights only; portable; you recreate the architecture in code) rather than pickling the whole object (fragile across refactors).

    Tokenisation bug (preview of Topic 5)

    A domain term like "hyperglycemia" gets split into 6 fragments. First inspect tokenisation; if justified, add_tokens to the tokenizer and resize_token_embeddings before fine-tuning.

    Remember
    • Train ↓ / val ↑ = overfit. Both flat-high = underfit or broken pipeline.
    • NaN or growing grad-norm = exploding gradients → clip + lower LR.
    • Always: zero_grad, eval(), no_grad().
    • Low GPU use + busy CPU = data loading.
    • If it can't overfit one batch, there's a bug.

    4. GPU memory and scaling

    Where memory goes, how to shrink it, and how to split work across GPUs.

    The one-line ideaMemory = parameters × bytes per parameter, plus extra for training state and activations. Know the numbers and the four ways to split a job across GPUs.

    Bytes per parameter

    FormatBytes7B model weights
    fp32428 GB
    fp16 / bf16214 GB
    int817 GB
    4-bit0.53.5 GB

    Formula: weight memory = parameters × bytes per parameter. This is the minimum; KV cache, activations and overhead come on top.

    Why training needs much more than inference

    Mixed-precision training with Adam keeps, per parameter:

    ItemBytes
    fp16/bf16 weights2
    fp16/bf16 gradients2
    fp32 master weights4
    Adam momentum (m)4
    Adam variance (v)4
    Total≈ 16 bytes/param (before activations)
    • 1B params ≈ 16 GB; 7B ≈ 112 GB for training state alone. That's why big models need sharding (below).
    • Nuance: 16 B/param is an estimate for one setup (full training, mixed-precision Adam), not a constant. Optimiser choice, sharding, precision, frozen parameters (e.g. LoRA trains very few) and activations all change the real number.
    • Activations (intermediate results kept for backprop) grow with batch size and sequence length.

    OOM toolbox ("CUDA out of memory")

    ToolWhat it doesTrade-off
    Smaller batchFewer activationsNoisier updates
    Gradient accumulationSum gradients over several micro-batches before step(); simulates a big batchMore forward/backward passes → slower
    Mixed precision (bf16/fp16)Halves many tensorsfp16 needs loss scaling (below)
    Gradient (activation) checkpointingThrows away activations and recomputes them in backward passMuch less memory, about 20–30% slower
    Shorter sequencesActivations shrinkLess context
    Things that make it worse Longer sequences, bigger batch, switching SGD → Adam (two extra states per parameter).

    fp16 vs bf16

    • fp16: more precision (mantissa bits), small exponent range → can overflow/underflow → needs loss scaling.
    • bf16: same exponent range as fp32, less precision → much more stable, usually no loss scaling.

    Splitting work across GPUs

    StrategyIdeaUse when
    Data parallel (DDP)Full model copy per GPU; split the batch; sync gradientsModel fits on one GPU; you want throughput. The baseline.
    FSDP / ZeROShard parameters, gradients and optimiser state across GPUsModel state doesn't fit on one GPU
    Tensor parallelSplit a single big matrix multiply across GPUsWithin a node, fast links (NVLink)
    Pipeline parallelDifferent layer groups on different GPUs; microbatches flow like an assembly lineVery deep models. Idle gaps ("bubbles") reduce utilisation
    DDP job hangs at end of epoch 1, no error One rank didn't reach the collective sync point (uneven batch counts, an exception, a conditional branch). Eventually an NCCL timeout. Check rank desynchronisation first.
    Remember
    • 7B fp16 = 14 GB; 4-bit = 3.5 GB; training ≈ 16 B/param.
    • Checkpointing: memory ↓, time ↑.
    • bf16 is the stable one.
    • DDP = copy model, split data. FSDP/ZeRO = shard the state.

    5. How LLMs work (what engineers need)

    Tokens, attention, prefill vs decode, the KV cache. These explain cost, latency and memory in later topics.

    The one-line ideaAn LLM turns text into tokens, predicts the next token, appends it, and repeats. Almost every cost, speed and memory question is a consequence of that loop.
    text → tokens (IDs) → embeddings → transformer layers (attention) → next-token probabilities → pick one → append → repeat (this is "autoregressive" generation)

    Tokens

    • Text is split into subword tokens. Rare domain words and SKU codes fragment into many pieces, which hurts the model.
    • Languages differ: some need many more tokens per word than English, so the same content costs more and is slower. Measure tokens per representative word/request, by language.
    • Cost and limits are counted in tokens, not words.

    Attention and context

    • Standard (full) self-attention compares every token with every other token, so cost grows roughly with the square of sequence length (why long prompts are expensive in prefill). Nuance: sliding-window, sparse and linear-attention variants exist to reduce this for long contexts.
    • Lost in the middle: models use the start and end of a long prompt better than the middle.
    • Context rot / bloat: hundreds of old turns and big tool outputs add noise, cost and latency. Summarise or drop old turns, compress tool outputs, retrieve only what's needed.

    Prefill vs decode (two phases of inference)

    PrefillDecode
    WhatProcess the whole prompt in parallelGenerate output one token at a time
    Usually limited byComputeMemory bandwidth (reading weights + KV cache each step)
    Shows up asTime to first token (TTFT)Tokens per second

    KV cache

    • For each past token the model stores its attention Keys and Values so it doesn't recompute them each step. That's the KV cache.
    • Size ≈ 2 × layers × n_kv_heads × head_dim × sequence length × batch × bytes
    • It grows with context length × number of concurrent conversations.
    • Server fits the weights but crashes with many long chats? Inspect KV-cache allocation and concurrency, not the weights.
    • GQA (grouped-query attention) shares K/V heads across groups of query heads → much smaller KV cache. (That's why the formula uses n_kv_heads, not the full head count or d_model.)

    Mixture of Experts (MoE)

    A model with 200B total parameters that activates 20B per token: compute per token ≈ the 20B active, but memory must still hold all 200B.

    Quantisation

    • Store weights in fewer bits (16 → 4): less memory, and often faster decode because fewer bytes are read from memory. Speed is not guaranteed: it depends on hardware support, the quantisation format, kernels and batch size.
    • Cost: quality can drop, especially on maths/code and small models (outlier values get clipped).
    • Weight-only quantisation shrinks weights; weight-and-activation quantisation shrinks both.
    • Response when quality drops: evaluate on your task at several precisions (latency + quality + cost); try a higher-bit or mixed-precision format. Don't ship a regression.
    Remember
    • Attention cost ~ length²; prefill = parallel, decode = sequential.
    • KV cache = weights' hidden sibling: grows with context × users.
    • GQA shrinks KV cache; MoE saves compute, not memory.
    • Quantise → measure on your task.

    6. Adapting LLMs: training stages and fine-tuning

    How a raw model becomes an assistant, and when you should (not) fine-tune.

    The one-line ideaFine-tuning mainly changes behaviour (style, format, skills). It is a poor way to keep changing facts current; use retrieval for those. This is a rule of thumb: the two often work together.

    The three training stages

    StageDataTeaches
    1 Pre-trainingHuge raw text, next-token predictionLanguage and general knowledge. Fluent, but ignores instructions
    2 SFT (supervised fine-tuning)Curated prompt → response pairsFollowing instructions and formats; turns a base model into an assistant
    3 AlignmentPreference pairs (chosen vs rejected) or checkable rewardsHuman preferences and safety

    Alignment methods

    • RLHF with PPO: train a separate reward model, then optimise against it. More moving parts, and sensitive to tuning.
    • DPO: learns directly from chosen/rejected pairs, no separate reward model. Simpler to set up, which is why it is popular.
    • Nuance: simpler does not mean better. Results depend on the preference data, hyperparameters and setup. One study (Xu et al., 2024) found a well-tuned PPO beat DPO on several benchmarks. The exam fact is only that DPO needs no separate reward model.
    • RLVR (RL with verifiable rewards): reward only when a deterministic checker passes (maths answer matches, unit tests pass).
    • Distillation: a small model learns from a stronger teacher's outputs.

    LoRA and QLoRA

    • LoRA: freeze the big base model; train tiny low-rank adapter matrices. Cheap, small files. (Hyperparameters: rank and alpha control adapter capacity and scaling.) Library: Hugging Face PEFT.
    • QLoRA: same, but the frozen base is stored in 4-bit, so a huge model fits on far smaller hardware. Be realistic, though: a 70B model on one 48 GB GPU needs a careful memory estimate, not a hope.

    Risks of fine-tuning

    • Catastrophic forgetting: narrow data overwrites general ability. Mitigate: LoRA, low learning rate, mix general instruction data into your domain data, test on broad regression sets.
    • Overfitting on a small narrow dataset.
    • Data quality beats quantity: 800 curated, diverse, deduplicated examples can beat 20,000 noisy duplicated ones.
    • Never stops talking? The end-of-sequence (EOS) token was missing or masked in the training format, so the model never learned to stop.

    Fine-tune vs RAG vs prompt (decision)

    NeedUse
    Quick improvement, clearer instructionsPrompt / context engineering first
    Private, changing facts; must cite sources; update without retrainingRAG
    Consistent style/format, specialised stable skill, sometimes cheaper small modelFine-tuning
    Facts that change weekly + citationsNot fine-tuning. Fine-tuning bakes static knowledge into weights
    Both: specialised domain and fresh factsCombine them: fine-tune for domain language, format and task skill; RAG for current, citable facts

    Nuance: fine-tuning can also improve domain adaptation and task capability, not just style. Choose by evidence from your evals, not by slogan.

    Remember
    • Pretrain → SFT → alignment (DPO = no reward model).
    • LoRA = small adapters; QLoRA = adapters on a 4-bit base.
    • Fine-tune behaviour, retrieve facts.
    • Forgetting: low LR, LoRA, mix in general data.

    7. RAG: retrieval-augmented generation

    Example B: the policy assistant. This is the most common LLM architecture, and most "wrong answer" bugs live here.

    The one-line ideaDon't make the model memorise your documents. Find the relevant passages at question time and hand them to the model to answer from.
    INGEST (offline): parse PDF → chunk → embed → store in vector index (+ metadata) QUERY (live): question → filter/rewrite → retrieve top-k → rerank → build prompt → generate → verify/cite

    Ingestion

    • Parsing: multi-column PDFs, tables, diagrams need layout-aware parsing (plus a vision/image path for visuals). Naive text extraction scrambles reading order.
    • Chunking: fixed-size character splits cut sentences and tables in half and strip context. Use structure/semantic-aware chunking.
    • Freshness: track document versions/hashes, re-embed changed content, delete removed chunks. Otherwise old answers keep appearing.
    • Ingestion lag: bot says "I don't know" about a file uploaded 5 seconds ago? Ingestion is asynchronous; it's not indexed yet.

    Retrieval

    MethodGood atWeak at
    Dense (embeddings)Meaning, paraphrasesExact codes, SKUs, acronyms, rare names
    Sparse (BM25 keyword)Exact termsSynonyms / paraphrase
    Hybrid (both)Both; usually beats pure vector
    • Same embedding model for documents and queries. Different models live in incompatible vector spaces, so similarity is meaningless.
    • Metadata filters (country, team, permissions) must be applied server-side before retrieval. A prompt is not an access-control boundary.
    • Reranker (cross-encoder): stage 1 retrieves many candidates cheaply; stage 2 scores each against the query jointly, slower but far more accurate, and puts the best on top.

    Generation and trust

    • Instruct the model to answer only from evidence; require citations.
    • Question outside the knowledge base → say the evidence is insufficient or ask a clarifying question (abstain), don't guess.
    • Even a relevant cited document can be misquoted: verify dates, figures and identifiers against the source.
    • Long contexts: relevant passage in the middle gets ignored (lost in the middle). Rerank, trim, reorder.

    Measuring RAG: the RAG triad (RAGAS-style)

    • Context relevance: did retrieval bring back relevant material?
    • Groundedness / faithfulness: is the answer supported by that material?
    • Answer relevance: does it actually answer the question?
    • recall@k: is the correct evidence anywhere in the top k results? If not, retrieval failed.

    Debugging table (always: retrieval first, then generation)

    SymptomLikely stageFix
    Works with hand-fed context, fails end-to-endRetrievalChunking, embedding match, filters, top-k
    Right paragraph not in top-kRetrieval (recall@k)Better chunks, hybrid search, reranking, query rewriting
    Right passages, wrong orderRankingReranker
    Exact SKU / part number missedDense-only retrievalHybrid (add BM25)
    Claims not in the sourcesGenerationGrounding instructions, citations, groundedness check, abstain
    Old policy still quotedIngestionVersioning, re-embed, delete stale chunks
    Brand-new doc unknownIngestion lagWait for async index / show indexing status
    Remember
    • Retrieval failures can't be fixed by prompts or bigger models.
    • Hybrid for exact terms; rerank for order; same embedding model; filters server-side.
    • Abstain when evidence is missing.
    • Triad: context relevance, groundedness, answer relevance.

    8. Building with LLM APIs: prompts, structure, cost

    Making an LLM feature reliable, fast and affordable.

    The one-line ideaTreat the model like an unreliable, billed-per-token external service: validate what comes back, protect yourself from outages, and do the cost maths.

    API or self-host?

    • Start API-first to find product fit and build evals. Consider self-hosting when sustained volume, data residency or customisation justify it.
    • Honest cost comparison includes idle GPU time, redundancy, operations and engineering time, not just the GPU's hourly price.
    • Provider changes its model version → run regression evals on your golden set, track versions, roll out cautiously. Pin versions where possible.

    Structured output (JSON)

    • Use schema-constrained output where available (function calling, JSON mode, Pydantic) and validate before use.
    • Valid schema ≠ correct or authorised. A perfectly formed JSON containing another tenant's user ID is still a security bug. Check meaning and permissions too.
    • Schema failure: bounded repair. Re-prompt with the exact validation error 2–3 times, then fail safely. Never retry forever.

    Cost

    • Cost = tokens ÷ 1,000,000 × price per 1M tokens. Example: 2,000 input tokens × 500,000 requests = 1B tokens = 1,000M × $3 = $3,000/month.
    • Prompt caching: put the stable parts (system prompt, tool schemas, shared context) first so the provider can reuse them cheaply; variable user text goes last.
    • Model routing: send easy tasks to the smallest model that passes your evals; reserve the big model for hard cases.
    • Jobs that can wait hours (nightly classification) → batch/async APIs, which are cheaper.
    • Context management: long histories cost money and reduce quality. Summarise old turns, compress tool outputs.

    Reliability

    • Every external call needs a timeout (a hung provider call must not hang your app).
    • Rate-limit (429) errors → exponential backoff with jitter, queues, fallback model, graceful degradation. Circuit breakers stop hammering a failing service.
    • 10,000 requests/day → plan for limits, retries, monitoring and cost.

    Latency

    • TTFT (time to first token) drives how fast it feels. Streaming helps perception even when total time is the same.
    • Slow response? Break it down first: retrieval, queueing, network, TTFT, generation time. Optimise the biggest piece.

    Caching answers

    CacheRiskSafeguard
    Exact cacheStale answer; answer for the wrong user/permission scopeInclude user/tenant/context in the key; expire when sources change
    Semantic cache (similar questions)"Similar" but actually different question → wrong answerCareful similarity threshold; scope by user/tenant; invalidate on data change

    Trustworthy UX

    When uncertain: show sources, say it's unsure, allow correction, make actions reversible. Don't project false certainty.

    Remember
    • Validate output, then check meaning and permissions.
    • Stable prefix first (caching); smallest passing model (routing).
    • Timeout + backoff with jitter on every call.
    • Measure TTFT and break latency into parts.

    9. Agents, tools and security

    When the model can do things, mistakes and attacks become actions.

    The one-line ideaAssume the model can be tricked. Don't rely on instructions to keep it safe; limit what it can do using code outside the model.

    Workflow or agent?

    • Workflow: steps are fixed in code (retrieve account → calculate → ask confirmation → submit). Simpler, cheaper, easier to test.
    • Agent: the model chooses actions dynamically. Use only when the steps genuinely can't be known in advance.
    • Rule: use the simplest pattern that meets the need.

    Tool design

    • Few, well-named, narrowly scoped, typed tools. Not one broad "run any command" tool.
    • Authorisation lives in code against the end user's identity (payment tool, "colleague's leave balance"). A correctly formed tool call can still be unauthorised.
    • Loops: max-steps budget, detect repeated identical calls, return structured error messages the model can recover from, timeouts.
    • High-impact actions (database writes, payments): pause, show a human-readable dry-run diff, get approval, then commit.

    Prompt injection

    • What: untrusted text (user input, a web page, a retrieved document saying "ignore previous instructions") tricks the model into following the attacker.
    • Principle: retrieved content is data, not instructions. Enforce permissions and tool policies outside the model.
    • A filter or system-prompt warning alone is bypassable.
    The lethal trifectaAn agent that has (1) access to private data, (2) exposure to untrusted content and (3) a way to send data out can be made to leak. Robust defence is architectural: remove at least one of the three.
    • MCP servers/tools: treat as untrusted code; give least-privilege credentials; review security.
    • Defence in depth: least privilege + approval for risky actions + untrusted-data handling + monitoring.

    Guardrails vs evals

    GuardrailEval
    WhenRuntime, inline, real timeOffline or asynchronous
    JobBlock PII leaks, jailbreaks, toxicity, off-topic before the user sees itMeasure how often the system behaves correctly
    Needs to beFast, often deterministicThorough

    A guardrail that blocks real users has a false-positive problem: measure its false-positive rate alongside detection (TPR/TNR). Version it and monitor it.

    Evaluating agents

    1. Score the end-to-end outcome first (did the task get done?).
    2. Then inspect the trajectory: tool choice, arguments, errors, wasted steps.
    3. Check claims vs tool results. "Your leave is booked" when the tool returned an error is a failure. Verify outcomes.
    Remember
    • Fixed steps → workflow, not agent.
    • Authorisation in code, not in the prompt.
    • Trifecta: remove one leg.
    • Approve high-impact actions with a diff.
    • Guardrail = runtime; eval = measurement.

    10. Evaluating LLM apps (evals)

    The biggest topic in the quiz. It's one workflow; learn the order and the questions get easy.

    The one-line ideaDon't start with a generic score. Read real traces, name the ways it fails, rank them, then build a cheap check for each and run them on every change.

    The eval workflow (in order)

    1 Collect traces (a trace = one full run: input, retrieval, tool calls, output) 2 Sample well: random + outliers + negative feedback + long/retry-heavy + clusters of similar queries 3 Open coding: read, write free-text notes on what went wrong 4 Axial coding: group the notes into named FAILURE MODES 5 Prioritise: frequency × impact (rare but severe privacy leak outranks common typo) 6 Build an evaluator per failure mode (code check first, LLM judge if needed) 7 Run in CI on every change, monitor in production, repeat
    • "90% helpful" on a single score tells you nothing to fix. Look at traces and failure modes.
    • A sample of only happy-path traces misses outliers, negatives and edge cases.
    • No users yet? Generate synthetic inputs systematically: define dimensions (feature, scenario, persona) → combine them → generate natural inputs. Decide correctness separately.
    • Long conversation fails at turn 8? Find the first upstream failure, replay turns 1…N−1 and test turn N, shrink to the smallest reproducer, repeat runs (outputs vary).
    • Benchmark-reality gap: strong benchmark but unhappy users → eval doesn't reflect real workflows. Add real failures to the set (see the Hard-mode question about 82% → 90%).
    • Multilingual: test every supported language, dialect and mixed-language request.

    Choosing the evaluator

    Failure typeEvaluator
    Objectively checkable: valid JSON, required disclaimer text, exact number equals truthCode assertion / schema validator: cheap, deterministic, first choice
    Needs judgement: tone, empathy, "captures the main idea"LLM judge (one failure mode per judge, clear definition, pass/fail)
    Did the agent finish the task?Outcome check, then trajectory
    Real user impact of a changeA/B test on real behaviour

    Evaluation ladder: unit checks → human/model review → A/B tests (task completion, escalations, retention).

    Can you trust the LLM judge?

    • Single-purpose judge: one failure mode each. A narrow rubric is clearer and easier to validate.
    • Validate against human labels:
      • TPR = share of real failures the judge catches
      • TNR = share of real passes it correctly passes
    • Accuracy lies on imbalanced data: if only 2% of cases fail and the judge says "Pass" to everything, accuracy is 98% but TPR = 0%.
    • Agreement between two humans: Cohen's kappa (chance-adjusted). For 3+ annotators: Fleiss' kappa or Krippendorff's alpha.
    • Don't over-tune the judge prompt on one set. Keep a held-out test set to avoid overfitting.
    • Judge flags more failures than experts think? Validate TPR/TNR, then correct the estimate cautiously. The correction is meaningless if TPR + TNR is close to 1 (no better than chance).

    Judge biases

    BiasMeaningCheck
    Position biasPrefers the first (or second) answerSwap the order; count a win only if it holds both ways
    Verbosity biasPrefers longer answersControl for length
    Self-preferenceRates its own model family's output highlyUse a different family; validate against humans

    Statistics you must recognise

    • Small sample, no uncertainty: "90% pass on 50 cases" needs a confidence interval (Wilson interval behaves well for small n or rates near 0/1).
    • Two versions on the same cases (paired pass/fail) → McNemar's test (uses cases that flipped).
    • Run-to-run noise: repeat runs; outputs vary.
    • Changing prompt, model and retrieval at once? You can't attribute any gain. Change one thing, rerun the same eval set, report per-failure-mode changes plus latency and cost.

    Evals in CI and production

    • Golden dataset (100–500 verified examples): run automatically on every prompt, retriever or model change → regression tests.
    • A prompt change improves the average but breaks a critical failure mode? CI should block if that mode is designated release-blocking (data leaks, unconfirmed actions). Tone regressions may only warn.
    • Saturated suite (passes for months): make it harder or retire it, but keep high-stakes checks (data leaks, wrong pay info).
    • Sampling live traffic: cheap deterministic checks on every trace; expensive LLM judges on a sample or nightly batch (risk/stratified sampling).
    • Prompt optimisers: only after you have a reliable eval set. Otherwise they overfit a weak target.
    Remember
    • Traces → open coding → axial coding → failure modes → frequency × impact.
    • Code check first; LLM judge for judgement only.
    • Validate judges with TPR/TNR (not accuracy), kappa for humans, swap order.
    • Intervals for small n; McNemar for paired; one change at a time.
    • CI blocks critical regressions.

    11. Serving and deployment

    Getting a model in front of users quickly, cheaply and safely.

    The one-line ideaServing is a balancing act between latency (how long one user waits) and throughput (how much work the system does in total).

    Latency vs throughput

    • Latency: time for one request. Report percentiles (p50, p95, p99), not averages. Tail latency is what unhappy users feel.
    • Throughput: requests or tokens per second across all users.
    • High tokens/s but users complain → look at p95/p99 latency and queueing.
    • For LLMs also track TTFT (time to first token).

    LLM serving techniques (vLLM-style engines)

    TechniqueProblem it solves
    Continuous batchingNew requests wait for the whole batch to finish. Fix: insert a new request the moment any sequence finishes → GPU never idles
    PagedAttentionKV cache wastes memory when reserved as big contiguous blocks. Fix: store it in pages, so more concurrent requests fit
    Speculative decodingDecode is slow, one token at a time. A small draft model proposes several tokens; the big model verifies them in one pass. Same output quality, faster
    KV cachingAvoids recomputing attention for past tokens (see Topic 5)
    QuantisationFewer bytes read per token → often faster decode, but only if hardware/kernels support the format. Always measure both speed and quality

    A naive Hugging Face generate loop is fine for experiments but not for high-concurrency production traffic.

    Why is it slow? (measure first)

    • Break the request into: queueing, retrieval, TTFT, generation, network.
    • Latency spikes every few minutes: autoscaling cold starts on GPU pods, garbage collection pauses, queue bursts, connection-pool exhaustion.
    • Profile before optimising.

    Safe releases

    PatternWhat users seePurpose
    Shadow deploymentNothing. A copy of live traffic goes to the new model; outputs are logged onlyCompare quality/latency risk-free
    Canary releaseA small share of real users (e.g. 1–5%) get the new modelCheck live business metrics, then ramp up
    Blue-greenSwitch between two full environmentsInstant rollback

    Always: version the model, staged rollout, health checks, a tested rollback path. A typical order is shadow → canary → full.

    Remember
    • Percentiles, not averages.
    • Continuous batching = no waiting; PagedAttention = KV cache without waste; speculative decoding = draft + verify.
    • Shadow = invisible copy; canary = few real users.
    • Measure where the time goes first.

    12. Production ML, drift and governance

    After launch: models quietly rot. This is the "keep watching it" part of the lifecycle.

    The one-line ideaA deployed model faces a changing world. Monitor inputs, outputs and outcomes; investigate before retraining; keep records so you can explain and reproduce what happened.

    Three different ways it goes wrong

    ProblemPlain meaningFraud example
    Data drift / covariate shiftInput distribution P(X) changes; relationship to the label is unchangedA new payment app suddenly brings many small transactions
    Concept driftThe relationship P(Y|X) itself changesFraudsters change tactics; the same-looking transaction now means something else
    Training-serving skewFeatures computed differently offline vs live, so the model sees inputs it never trained onTraining used a pandas job; production recomputes "avg spend" with different logic
    • Skew fix: share the same feature code/definitions (a feature store helps) and test for parity.
    • A feature that isn't available at prediction time (see leakage, Topic 1) fails or misleads in production.

    What to monitor

    • Input distributions, prediction distributions, labels (when they arrive), quality metrics, business outcomes, data-pipeline health.
    • Per slice/segment. Aggregates hide regressions.
    Sudden input shift, what first? Check data quality and upstream/operational changes → assess impact → maybe fall back to a safer model/rules → then decide whether to adapt or retrain. Drift is a signal to investigate, not an automatic retrain button.

    Logs, audit and governance

    • PII in logs: minimise collection, redact/mask, restrict access, set retention rules.
    • Auditable AI feature: record versioned model and prompt IDs, relevant inputs/outputs (with privacy controls), retrieval references, evaluation metadata. Enough to reproduce behaviour.
    • High-stakes use (e.g. employment decisions): document intended use, risk controls, audit logs, fairness testing, human review, a named accountable owner. Legal duties depend on jurisdiction.
    • Reproducibility: record model, adapter, tokenizer, prompt and eval results together.
    • Explainability for regulated stakeholders: use appropriate methods (e.g. SHAP) and document their limits.

    Eval vs real life

    Strong benchmarks but unhappy users → you haven't evaluated against real user workflows and business outcomes. Link offline scores to task success and user impact.

    Remember
    • Covariate shift = inputs change; concept drift = the rule changes; skew = offline ≠ online features.
    • Investigate, don't auto-retrain.
    • Log with privacy; audit with versions.
    • Monitor by slice.

    Numbers and formulas

    • Weights memory = params × bytes. 7B fp16 = 14 GB; 4-bit = 3.5 GB.
    • Training ≈ 16 bytes/param (2+2+4+4+4) before activations.
    • Token cost = tokens ÷ 1M × price.
    • Precision = TP/(TP+FP); Recall/TPR = TP/(TP+FN); TNR = TN/(TN+FP).
    • KV cache ≈ 2 × layers × n_kv_heads × head_dim × seq × batch × bytes.
    • Failure priority = frequency × impact.
